1. The toy game

Think of each node as one whole KQK position: piece squares plus whose turn it is, for example K_W=h1 Q_W=h2 K_B=e4, Black to move. An arrow is one legal move. White-to-move positions are white circles, Black-to-move positions are black circles, and moves alternate between them.

Real KQK has hundreds of thousands of nodes. This one has 10 plus three end states, which is small enough to compute by hand:

  • mate: Black to move and checkmated. Value −1 for the side to move (Black).
  • draw: Black captured the queen, so only kings are left. Value 0.
White to move Black to move end of game

Look at B2: Black can capture the queen there (move to draw). White's first move from S should avoid giving Black that chance. A correct solver has to discover this on its own.

2. The Bellman backup

A backup is one small calculation at one position: "if I already knew the values of the positions I can move to, what is this position worth?" You look one move ahead, read the values of the next positions from the table, and write the best result into this position's entry.

One player first

In a maze, a square's value is the best neighbour's value minus the cost of one step. The single-agent Bellman equation says the same thing:

V(s) = max over moves a of [ reward(s, a) + γ · V(next) ]

Two players: minimax

In chess the two sides want opposite things. Score everything from White's point of view: White picks the move with the highest value and Black picks the lowest. Take B1 (Black to move), whose moves lead to W2 and W3. Suppose we already know W2 is worth +0.9 for White and W3 is worth +0.729:

Black to move, so take the min (values from White's view) V_white(B1) = min( 0.9 · V_white(W2), 0.9 · V_white(W3) ) = min( 0.9 · 0.9, 0.9 · 0.729 ) = min( 0.81, 0.656 ) = 0.656 Black heads for W3

Negamax: one rule for both sides

Writing max for one side and min for the other gets messy. Instead, store every value from the point of view of the side to move. What is good for my opponent is bad for me, so a value flips sign every time you cross an arrow:

V(s) = max over moves of − γ · V(next)

Read it from White's seat:

  1. Every value in the table is from the point of view of the side to move in that position.
  2. After any White move it's Black's turn, so V(next) is how good that position is for Black.
  3. Zero-sum: what's good for Black is equally bad for White, so the same position is worth −V(next) to White.
  4. White picks the move with the highest −V(next), which is the move that leaves Black worst off.
  5. One move later Black uses the exact same rule from its own seat. One formula covers both sides.

The minus sign means "switch seats". Plain minimax keeps everything from White's view, with White taking the max and Black the min. Negamax gives the same numbers, stored from the mover's side, with a single max.

Same example. Now W2 and W3 are worth +0.9 and +0.729 to White, the side to move there:

V(B1) = max( −0.9 · 0.9, −0.9 · 0.729 ) = max( −0.81, −0.656 ) = −0.656 bad for Black, the side to move

It gives the same answer as minimax with the sign flipped (−0.656 for Black is +0.656 for White), and every position uses the same rule. That's why our solver uses negamax.

Why the 0.9 (γ)?

Without it, every win is worth +1, whether it's mate in 1 or mate in 40. The winning side then has no reason to make progress: in our graph, W4 and B4 could shuffle back and forth forever, since every position in the loop counts as "winning". With γ = 0.9, each extra move shrinks the value:

SituationValue (side to move)
Checkmated−1
Mate in 1 available+0.9
Every move allows mate in 1−0.81
Mate in 2+0.729

So the winner prefers faster mates and the loser prefers slower losses. That's why Black at B1 goes to W3: it loses in more moves.

This matches real chess. Against a perfect opponent a lost position stays lost however long you resist. Real opponents make mistakes, though, so dragging out a loss gives them more chances to go wrong, and a fast win gives them fewer. Tablebase-perfect defence works the same way: it always picks the longest resistance.

Our real solver stores "win/draw/loss + plies to mate" instead of a γ-number. The two carry the same information, but γ is easier to see in a small example.

A backup only reads the neighbours' current values. They don't have to be correct yet. If they're still guesses, the backup gives an improved guess. Value iteration and RTDP both do backups and differ only in which positions get backed up, and in what order.

3. Value iteration: back up every position, every sweep

Start with every value at 0 (a guess). End states are exact from the start. One sweep backs up all 10 positions using the previous sweep's values. Repeat until a sweep changes nothing. Step through it:

Before sweep 1: all guesses are 0
value changed in this sweep+ good for side to move− bad for side to move
Sweep 0Backups so far 0
Press Next sweep.

The values ripple outwards from the mates, one move per sweep. This is your breadth-first search from the terminal states. Note B3 in sweep 2: two of its moves lead to mate-in-1 positions, but its third move (to W5) still looks like 0. A position is only proven lost once every escape is closed, so B3 has to wait until sweep 4.

The cost: each sweep does 10 backups, but most of them change nothing. That's 60 backups in total, and only 10 of them did anything useful. On real KQK, the retrograde analysis we'll implement fixes this: it walks moves backwards from the mates and backs up a position only when one of its neighbours has just been resolved. It produces the same table and the same values as value iteration, without the wasted backups.

4. RTDP: back up only where play goes

Real-time dynamic programming uses the same backup, but it doesn't sweep. Instead it plays games, called trials:

  1. Start at S.
  2. Back up the current position using the table's current values.
  3. Play the move that backup says is best. Both sides do this, so Black also plays its best move by the current table.
  4. Repeat until the game ends, then start a new trial from S.

When moves are tied (common at first, when everything is 0), pick the move this position has tried least often. That simple rule makes sure untried moves eventually get explored.

RTDP spent no effort on them, which is the whole point.

5. Your three questions

Does RTDP start from random positions, or from positions a real game would reach?

You choose. The set of start positions is an input to RTDP, and it defines what "relevant" means. RTDP's guarantee (Barto, Bradtke & Singh, 1995) is that values become exact on the positions that come up when playing well from those starts. Positions that good play never reaches can stay wrong forever.

  • Start from one position (as above): only a slice of the graph matters.
  • Start from positions that arise in real games: you get correct play wherever games actually go.
  • Start from every position: everything is relevant, so RTDP has to solve the whole table, and there's no saving.

For our experiment, we'll pick a sample of start positions (say 1,000 random legal KRK positions with White to move) and measure how many distinct positions RTDP touches before its play from those starts matches the exact table. In a 3-piece ending, almost any position can come up in a real game, so the saving may turn out modest. That's still a real, reportable measurement.

If the starts are random, how can it converge faster than value iteration?

It doesn't solve the whole table faster. It gets the positions you care about right faster, for two reasons:

  1. It skips positions that don't matter. W5 and B5 were never touched.
  2. It skips pointless backups. Sweep 1 of value iteration did 10 backups and only 2 changed anything, because the rest had no known neighbours yet. RTDP spends its backups along paths that lead to mates, where information is arriving.

It wastes some work too. Trial 1 backed up S, B2, W3 and B4 and learned nothing from them. And it needs exploration: if ties were always broken the same way, White could keep playing S → B2, see a "draw", and never try B1. That's why the tie-break uses the least-tried move. In the single-player theory, the fix is to start with optimistic guesses. For two players, we'll rely on exploration and check the results against the exact table.

For KQK and KRK, retrograde analysis is the fastest way to get the full table. RTDP is in the project because it shows the idea that scales: update only where play goes.

Aren't we still filling up the table?

Value iteration and RTDP need two different things:

Value iteration / retrogradeRTDP
Must list every position up front?Yes, in order to sweepNo. It only needs the move generator, to find the next positions from wherever it is.

For KQK we'll probably still allocate the full array, because it's small and makes the comparison with the exact answer easy. The number we report is how many entries RTDP actually writes. For full chess, even the dictionary is hopeless: a single game visits ~80 positions, but there are ~10⁴⁴ possible ones, and you almost never see the same position twice outside the opening. That's where the neural network comes in.

7. How the network learns from search

Yes, it's gradient descent. First, the four symbols, all per position and from the side to move's point of view:

SymbolWhat it isExampleRole
pThe network's own move probabilities, before any search: its quick first guess at which move to playQh7 0.2, Qa1 0.5, Kg2 0.3network output
vThe network's guess of who is winning: one number for the whole position, from −1 (loss) to +1 (win)+0.3network output
πMove probabilities after MCTS: each move's share of the search's visits. Better than p, because the search looked aheadQh7 0.7, Qa1 0.1, Kg2 0.2training target
zWho actually won the game this position came from+1, 0 or −1training target

p answers "which move?" and v answers "who's winning?". The network produces both in one pass, using one shared body with two heads. Training pushes p towards π (copy what the search found) and v towards z (predict the real result).

Here is the loop.

What one self-play game produces

At every position s in the game, MCTS runs, say, 100 simulations and counts how often it visited each move. Those counts, divided by 100, form π: the search's opinion of how good each move is. When the game ends, every position gets z: the final result from that position's side to move (+1 win, 0 draw, −1 loss). Each (s, π, z) goes into the replay buffer (your Phase 2 component).

What the network predicts

For the same position, the network outputs p (its own move probabilities, before any search) and v (its value guess). Training makes p look more like π and v look more like z:

loss = (z − v)² value: was the guess right about who wins? − Σ over moves π(a) · log p(a) policy: cross-entropy, match the search's move choice + c · ‖θ‖² keep the weights small θ ← θ − η · ∇θ loss one gradient descent step (η = learning rate)

One position, worked through

Say there are three legal moves. Before searching, the network liked Qa1 best. After 100 simulations, MCTS concluded Qh7 is much better. White went on to win the game, so z = +1.

MoveNetwork pMCTS visitsTarget πGradient on logit (p − π)Step moves it

With softmax and cross-entropy, the gradient on each move's raw score (logit) is simply p − π. Gradient descent subtracts it, so Qh7's score goes up and Qa1's goes down. For the value, the network said v = +0.30 but White won (z = +1). The gradient of (z − v)² is −2(z − v) = −1.4, so the step pushes v upwards. Real training does this on mini-batches of a few hundred random positions from the replay buffer, thousands of times.

It's the same update as the table, just smoothed

Suppose the "network" were just a table with one number per position. A gradient step on ½(target − V(s))² gives:

V(s) ← V(s) + η · (target − V(s))

That nudges the entry part of the way towards the target. With η = 1 it simply overwrites the entry, which is exactly what RTDP's backup did. A network uses shared weights instead of separate entries, so one step also shifts the values of similar positions. That's how it generalises to positions it has never seen, and also how it makes mistakes. Your KRK approximation experiment measures exactly this: train a network on positions where we know the exact answer, and see where the smoothing breaks.

The whole loop, in RL terms. MCTS takes the network's move choices and improves them by looking ahead: π is better than p. That's policy improvement. Training copies the improvement back into the network, the way a backup writes into the table. The next round of searches starts from a better network, finds even better moves, and so on. This is approximate policy iteration, the framing for the whole project.
